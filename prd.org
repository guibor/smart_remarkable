#+title: Smart Remarkable Paper Pro Deployment

* Requirements

- Run Smart Remarkable on a Developer Mode reMarkable Paper Pro with firmware 3.28.
- Keep the stock =xochitl= notebook application running; do not take over the display.
- Install runtime files only under encrypted =/home= and do not add a boot service.
- Send selected-note requests to the user's canonical OpenClaw =main= session rather than calling an LLM provider with an API key.
- Reuse the exact =agent:main:main= session with =whatsapp= message context so Smart Remarkable sees the same server-side history, memories, and agent tools as the user's WhatsApp conversation.
- Keep all conversation history and memory on the OpenClaw server; beyond the requested answer typed into the stock note, do not retain separate screenshots, output files, or a transcript on the tablet.
- Keep the OpenClaw Gateway private and never expose its operator endpoint or credential to the tablet or public web. The server-side bridge may authenticate to the loopback Gateway; the tablet reaches only the narrow loopback bridge through a one-shot SSH tunnel owned by a dedicated password-locked Unix account. That account must permit only client-local TCP forwarding to literal =127.0.0.1:18792= and deny remote TCP forwarding, StreamLocal forwarding, shell/exec/subsystem sessions, PTY, agent/X11 forwarding, tunnels, and user rc.
- Let the user lasso handwriting with the stock selection tool, submit through the configured explicit or pen gesture, and receive a stock text-box answer below it.
- Provide one reversible ReMagic/AppLoad tile that toggles the configured bounded worker. It must not create separate tiles for the three modes.
- Use the repository's existing =draw_text= implementation for answers; do not convert ordinary text into simulated pen strokes.
- Consume root-only volatile trigger files under =/run/smart-remarkable= even while the Paper Pro touch device is emitting continuous events, and remove them when the worker stops.
- Do not install the ABI-sensitive raw Xovi =llmbutton.so= LLM/Draw extension on firmware 3.28. A native-button candidate must use the firmware-specific QMLDiff/AppLoad path and add only the approved answer-here and agent actions, represented by exact stock reMarkable sparkle resources rather than text glyphs or custom assets.
- Refuse kernel-module loading by default and require the firmware-provided =/dev/uinput= device for this deployment.
- Keep Smart Remarkable and T.M.R. mutually exclusive, give Smart its own tunnel port, and stop Smart whenever stock =xochitl= stops.
- Keep Smart Remarkable's unauthenticated web server and debug/request logging disabled.
- Preserve a recovery path over key-authenticated Wi-Fi SSH.
- Resolve the Paper Pro framebuffer across every contiguous =/dev/dri/card0= mapping group and detached terminal frame allocation after each =xochitl= restart; reject malformed, looping, overflowing, or incompletely readable candidates instead of assuming the final graphics mapping is the display.
- Show exactly one Smart Remarkable entry in AppLoad; keep deployment stages, failed candidates, and timestamped rollback bundles in a root-only recovery directory outside AppLoad's scanned application tree.
- Make installer provenance independent of Git tracking state: deterministically hash every regular file placed in the AppLoad archive, verify the exact extracted file set and the separately transferred device installer before mutation, and retain the manifest plus its own hash in root-only recovery metadata. Untracked staged sources must receive the same coverage as tracked sources.
- Provide exactly three configurable runtime modes without adding duplicate AppLoad tiles:
  - =once=: accept one valid selection and exit.
  - =session-hold=: remain active for a bounded session; submit only when the user closes a native lasso, keeps the pen tip touching nearly still for the configured hold duration, and then lifts.
  - =session-auto=: remain active for a bounded session and submit every completed native lasso, with an explicit privacy warning because ordinary selection edits are also eligible.
- Keep the mode and non-secret session settings in a root-owned configuration file separate from the OpenClaw credential. The single AppLoad tile must toggle the current session on/off.
- In session modes, admit at most one request at a time, drop pen contacts that began while processing, suppress a still-active selection from duplicate submission, and clear cropped image/model scratch state after every success, error, or no-submit run.
- Allow optional native answer-here and agent selection-menu actions as the preferred explicit triggers only after a firmware-specific, read-only compatibility probe succeeds. They must use the stock notebook-with-sparkles and sparkles icons with no user-visible implementation labels. The QML patch may ask AppLoad to signal a trigger but must never contain credentials, call OpenClaw, load a kernel module, stop =xochitl=, or start at boot.
- Place two explicit native buttons immediately after the stock Copy action, in the order answer-here then agent. The first must use the firmware's stock sparkling-notebook resource and the second its stock sparkles resource. A tap must show immediate selected-state feedback, reject repeated taps while pending, clear every pending path when the menu changes visibility, times out, launch fails, or acceptance closes the selection, and—only after Smart Remarkable has captured the selected crop and the server bridge has accepted the idempotent request—dismiss the marquee through =SceneSelectionHandler.close()=. Neither button may invoke Copy, Cut, Delete, movement, or simulated touch coordinates; a capture or acceptance failure must leave the selection visible.
- Before upload, transiently prepare every selected-handwriting crop for vision: normalize the gray selection fill to a clean white background without erasing dark ink and upscale with aspect ratio preserved to a useful bounded resolution. Fingerprinting and model submission must use the prepared PNG; neither the source nor prepared crop may be written to a tablet file.
- Treat the two buttons as response destinations, independently of the existing =once=, =session-hold=, and =session-auto= trigger modes:
  - answer-here / =write_back=: deliver a "reading" acknowledgement followed by one WhatsApp message containing both OpenClaw's literal transcription and its answer, then insert only that same answer as stock text in the notebook.
  - agent / =whatsapp_only=: deliver the same acknowledgement and transcription-plus-answer WhatsApp message without selecting a tablet text tool, typing, drawing, or otherwise inserting a response into the notebook.
- Submit both button modes as one canonical OpenClaw agent turn through native Gateway =chat.send= with the selected PNG as an attachment, exact =agent:main:main= session routing, the startup-validated =expectedSessionRoutingContract= of =per-sender|main|main=, =deliver=false=, disabled command interpretation, and a unique idempotency key. A scope, main-key, or default-agent change must fail at startup and again at admission rather than silently recanonicalizing the main alias. Deliver the acknowledgement and final to the server-owned canonical WhatsApp route through a narrow plugin-owned Gateway method that requires a native provider receipt and deliberately omits transcript mirroring. Do not infer delivery from the synthetic =x-openclaw-message-channel= HTTP header or from successful agent completion alone.
- Before =chat.send=, bind protocol version, server-generated request id, response mode, and preflight-captured transcript id through =operator.admin=-scoped bind and clear methods. Store the pending authority as a bounded, realm-neutral JSON string in OpenClaw's host-owned run context so the Gateway startup registry, active prompt hooks, and pinned tool registry share one source of truth. Because ordinary plugin API methods close after =register=, every late bind-side get/set/clear must go through the plugin's registered agent-event run-context adapter: keep the complete operation and value only in the originating plugin instance's bounded private map, emit only a fresh random operation id on the plugin-owned control stream, and let the synchronous host subscription callback perform =getRunContext=, =setRunContext=, or =clearRunContext=. A set or clear succeeds only after exact host read-back; absent or asynchronous callback delivery, missing host methods, an emission/receipt mismatch, capacity exhaustion, or any exception must fail closed. This adapter is valid only for the exactly pinned OpenClaw 2026.7.1 synchronous event lifecycle; an OpenClaw upgrade must remain blocked until the late-call guard and same-stack callback ordering are re-audited. A pending record must expire after twelve minutes, activation must require the exact run id, transcript id, canonical agent, and canonical session key, and active authority must expire after fifteen minutes without extension. Before every bind, reconcile the bind-side index against host state: retain every still-live pending or active record, clear expired/malformed host records, and reject new reservations at 128 live records rather than evicting or undercounting them. Return a separate opaque binding handle, require it for cleanup, and clear host and local state after every bridge outcome so a stale cleanup cannot delete a newer binding. Also persist =systemInputProvenance= as =external_user= / =remarkable= / =smart_remarkable= for audit, keep =originatingChannel= and the canonical session origin as WhatsApp, and append a non-authorizing trusted transport instruction so the agent remains aware that the turn came from reMarkable even if a prompt hook is unavailable. Handwritten prompt text, ordinary WhatsApp input, model output, the transport instruction, a pending/expired record, a control-stream event, or a lookalike provenance marker must never authorize reMarkable-only tools.
- On a trusted reMarkable turn that asks OpenClaw to create, export, send, or place a document, make OpenClaw create a PDF or EPUB in its workspace and call a dedicated receipt-checked delivery tool that uploads the validated artifact to the user's ordinary reMarkable cloud library. The tool must be unavailable to ordinary WhatsApp turns; accept only regular non-symlink workspace files with matching extension and file signature; invoke the existing server =rm-sync= client without a shell or secret-bearing arguments; persist a fail-closed artifact idempotency receipt; and permit an upload claim only after a validated cloud document id/hash. OpenClaw must continue to report what it received and what it did through WhatsApp.
- Capture the canonical session id immediately before each new turn for exact-transcript recovery, but never pass that captured id back to =chat.send=: OpenClaw 2026.7.1 can rotate a current session to a mismatched caller-supplied id. Current bounded history and any live-final candidate are eligible only after the exact captured-session =<request-id>:user= anchor is verified. If the canonical key has remapped, prefer the captured active JSONL and otherwise consider at most 128 exact =.jsonl.reset.<safe-ISO-timestamp>= archives; open without following links, enforce file/line bounds, validate the first session record, and require one unique request anchor. Never inspect another session's transcript.
- For every accepted reMarkable turn, make WhatsApp visibly acknowledge that OpenClaw is reading the selection. The one canonical assistant final must use the server-owned strict ={"received_text":"...","response_text":"..."}= envelope. The bridge must reject malformed, empty, oversized, or control-character-bearing envelopes; render the successful WhatsApp final atomically as =I read:= plus a quoted literal transcription followed by the answer; and render =[unclear]= as an explicit inability to read rather than a guess. Do not mutate the canonical session's persistent verbose setting or expose raw commands, model reasoning, or tool outputs.
- Keep the full OpenClaw operator credential and WhatsApp delivery target on the server. Expose only a loopback-bound, narrowly authenticated reMarkable bridge through the existing forwarding-only SSH path, and store only its narrow credential on the tablet.
- Return only =response_text= to the tablet, and only for the first successful =write_back=; the WhatsApp-only =I read:= prefix must never be inserted into the notebook. A request is complete only when native OpenClaw delivery reports both the reading acknowledgement and the atomic transcription-plus-answer final as successful WhatsApp outcomes. Persistently reserve each request id before =chat.send= so a bridge/Gateway restart cannot create another canonical agent turn; a surviving incomplete reservation must fail closed without resubmission. Mark cached responses as replays, and require the tablet to suppress =draw_text= for every replay so duplicate client retries cannot create another agent turn, acknowledgement, final WhatsApp delivery, or notebook insertion. Ambiguous outcomes may omit a result but must never claim or manufacture exactly-once delivery.
- The native-button deployment must be fail-open for the stock UI: exact Qt symbols and object names are required, missing/mismatched prerequisites must disable injection, and a bounded watchdog plus preserved rollback must remove the extension if =xochitl= fails to remain healthy. Do not remount or write the system partition.
- Permit coexistence with other installed QMLDiff hacks only when every co-resident =.qmd= has an explicitly allowlisted filename, SHA-256, root ownership, and mode 0644. Missing, changed, symlinked, or additional =.qmd=, =.qrr=, or =.rcc= files must abort the button transaction before mutation.
- Keep =session-hold= usable without the injected button as the safe fallback. Holding means: draw and close the lasso while the pen is touching, keep its endpoint within a small movement radius for the configured duration (initially 800 ms), then lift; an ordinary immediate lift must remain a normal reMarkable selection and must not submit.
- Treat tunnel health as part of worker readiness. The AppLoad launcher must reject a stale =ready= marker unless the forwarded bridge health probe succeeds, restart one stale active transient unit at most once, and fail closed if the fresh bridge is still unhealthy. The runner must supervise both worker and tunnel, remove readiness and stop the worker as soon as either tunnel exits, and preserve the worker's own exit status when it finishes first.
- Firmware updates may deliberately return the tablet to stock operation. The
  supported workflow does not need to persist Xovi across an update; instead,
  regenerate the exact-firmware QMD and allowlist, reinstall through the
  documented bounded recipe, and preserve the existing =/home=-backed Smart
  Remarkable settings and worker bundle.

* Requirements that changed

- The first working deployment called OpenAI directly with an API key, then moved to an isolated =openclaw/default= session identified as =smart-remarkable-rmpp=. The supported backend is now =openclaw/main= with exact =agent:main:main= and =whatsapp= headers through the private OpenClaw Gateway; no provider API key or separate OpenAI =user= identity may be used by the tablet workflow.
- The first trial used a persistent corner-trigger Select Mode process. Paper Pro touch events caused repeated and tiny selections, so it was replaced by one-shot native-selection activation. Trigger state subsequently moved from shared =/tmp/llm_button_trigger= to root-only volatile =/run/smart-remarkable/llm_button_trigger= as part of the bounded three-mode design.
- The upstream trigger-file poll waited on a timer that was starved by continuous Paper Pro touch events. File consumption now runs before each event wait.
- The first successful native-selection response used =selection.json= and =draw_answer=, which rasterized text and retraced it as visibly distorted pen strokes. It was first changed to =selection_print.json=; the current OpenClaw workflow uses =selection_openclaw.json= with the same existing stock =draw_text= output path.
- Riddle's full-display takeover was originally replaced by Smart Remarkable's stock-UI integration. T.M.R. is now retained as a separately launchable diary, while Smart Remarkable coexists as a mutually exclusive, stock-UI assistant with one-shot and bounded-session modes.
- The first current-device validation inherited goMarkableStream's assumption that the final =/dev/dri/card0= mapping group belongs to the Paper Pro framebuffer. A later Riddle-driven =xochitl= restart changed allocation order: the final group then began with an invalid zero header while the valid frame chain was in the middle group. The supported locator must now probe all mapping groups and fail closed if none yields a complete frame.
- A subsequent =xochitl= layout split the terminal =0xd73000=-byte frame allocation away from both =card0= groups: the graphics-linked chain ended in an empty slot, while a standalone anonymous mapping began with the expected terminal =0xd73002= header. The locator must therefore validate large detached anonymous allocations through the same bounded header and full-frame checks; adjacency to =card0= is not a supported invariant.
- The first transactional installer preserved rollback application directories directly below AppLoad's scanned root. AppLoad correctly treated their copied manifests as extra applications, so three Smart Remarkable tiles appeared. Rollbacks must now remain preserved under =/home/root/.smart-remarkable-recovery=, which AppLoad does not enumerate.
- The armed AppLoad trial originally required a four-finger tap after lassoing. Live logs proved that Smart recognized the gesture, but xochitl cleared the gray marquee before the subsequent capture. The supported workflow now triggers from the lasso pen-up itself, after a short stock-UI render delay, so no second screen contact can dismiss the selection.
- The first pen-up design would have treated any pen tap after arming as the one-shot request and exited when no marquee existed. A no-marquee pen-up is now ignored, keeping the worker armed for the actual native lasso.
- The supported firmware-3.28 deployment originally prohibited any injected button because the raw Xovi =llmbutton.so= uses private Qt ABI and its development history includes =xochitl= crashes. The user has now explicitly requested a native button as the preferred interaction. The raw extension remains prohibited; the changed requirement permits only an exact-firmware QMLDiff/AppLoad candidate, staged through an inert canary, live compatibility checks, bounded monitoring, and automatic rollback.
- The original AppLoad workflow exited after every answer. It now needs configurable finite sessions so multiple selections can be handled from one AppLoad activation; one-shot behavior remains available.
- The original launcher used =smart-remarkable-once.service= with a fixed ten-minute limit. The single tile now targets =smart-remarkable-session.service= and chooses the bounded lifetime from the strict non-secret mode settings.
- The first functional firmware-specific button was inserted before Cut and left the lasso marquee/menu visible until later tool execution, so a successful tap looked unacknowledged and invited repeated taps. The revised requirement puts =LLM= directly after Copy, highlights it immediately, and closes only the already-captured selection through stock QML state—without copying or deleting the selected ink.
- The first button safety allowlist assumed Smart Remarkable was the only QMLDiff patch. A later inventory found ReMagic's =penLayerMemory-beta-3.28.0.163.qmd= installed while =quickSettingsTimer-beta-3.28.0.163.qmd= was absent. The current device-specific policy therefore requires the exact Pen Layer Memory file and hash, permits Quick Settings Timer only at its exact reviewed name and hash if it is installed later, and continues to reject every unrecognized QML artifact.
- The first OpenClaw integration used the OpenAI-compatible =/v1/chat/completions= endpoint and set =x-openclaw-message-channel: whatsapp=. That header supplies synthetic channel context but the endpoint explicitly does not deliver its result to WhatsApp; the tablet consumed the HTTP final and always called =draw_text=. The supported design now uses native Gateway =chat.send= for the canonical agent turn, a separate receipt-checked no-mirror WhatsApp delivery method, and distinct =write_back= and =whatsapp_only= destinations.
- The first native-menu design exposed only =LLM=. The user has now selected two explicit adjacent buttons rather than a hidden long-press or an AppLoad mode switch: =LLM= delivers to WhatsApp and writes the same final into the notebook, while =Send= delivers to WhatsApp only.
- The live ReMagic set changed again after the first coexistence review. The exact-device allowlist must now include the currently installed and hash-pinned Better TOC, Better TOC Collapse, Gestik, Ghostbuster, Pen Layer Memory, Quick Settings Timer, and TOC From Selection QMDs, while continuing to reject every additional, missing, changed, symlinked, wrongly owned, or wrongly moded QML artifact.
- The first native-Gateway bridge plan prepended =/verbose on= to each tablet turn to obtain tool-start messages. OpenClaw 2026.7.1 permits this admin-scoped directive to persist =verboseLevel= on =agent:main:main=, which would alter later WhatsApp behavior. The supported bridge instead disables command interpretation, sends one explicit delivery-checked "reading and working" WhatsApp acknowledgement, and sends the exact final separately without changing canonical session settings.
- The next bridge draft used OpenClaw core Gateway =send= for the acknowledgement and final. In OpenClaw 2026.7.1 that method derives the direct session and mirrors each outbound message into the canonical transcript, which would duplicate the agent's final answer in history. The supported design now keeps =chat.send deliver=false= as the sole transcript owner and uses a tightly scoped plugin Gateway method around the public durable outbound channel API with no =mirror= or session context.
- The first bridge service draft was a systemd user unit with =ProtectHome= and =ProtectSystem=. The live server runs systemd 249, where those protections are not enforced by the user manager. The production bridge is therefore a system service that immediately drops to =User=mdf=, receives one private writable =StateDirectory=, and keeps the rest of the home and system filesystem read-only; OpenClaw's Gateway remains an independent user service.
- The first AppLoad installer provenance recorded =git_head= plus =git diff --binary=, which omitted untracked deployment inputs and staged index changes even though several such files were bundled or executed. Git metadata is now contextual only: the supported installer hashes the final bytes of the complete staged file set, verifies the separately transferred device installer, and preserves the manifest trust chain in recovery metadata.
- The first two-button tunnel plan reused the server's ordinary =mdf= account and attempted to express a local-forward-only policy in one =authorized_keys= line. OpenSSH 8.9 uses one per-key flag for local TCP, remote TCP, and StreamLocal forwarding, so =restrict,port-forwarding,permitopen= cannot close the reverse and Unix-socket paths. The supported tunnel now uses a dedicated password-locked Unix account plus a validated =Match User= policy with =AllowTcpForwarding local=, =AllowStreamLocalForwarding no=, exact =PermitOpen 127.0.0.1:18792=, =PermitListen none=, and no sessions or interactive features.
- The first live two-button build uploaded the marquee crop exactly as rendered, so real selections as small as 109×46 and 139×46 pixels reached OpenClaw with gray selection fill at very low resolution. It also sent only a generic "reading and working" acknowledgement and expected the ordinary assistant final to serve simultaneously as the WhatsApp message and notebook insertion. The revised requirement transiently normalizes and enlarges selected handwriting; requires the single canonical assistant final to separate literal =received_text= from =response_text=; makes the WhatsApp final quote what OpenClaw read; and keeps only =response_text= eligible for notebook insertion.
- The first two-button presentation used literal =LLM= and =Send= labels. The current interaction uses the firmware's own sparkling-notebook icon for answer-here and sparkles icon for send-to-agent, preserving the same two explicit destinations and after-Copy order without fragile custom artwork or ambiguous implementation jargon.
- The first bridge prompt merely said that the selection came from reMarkable. That was useful context but not an authorization boundary and gave document requests no reliable artifact destination. The current requirement binds trusted plugin-owned admission state before =chat.send=, records durable input provenance separately from WhatsApp reply routing, and gates a receipt-checked reMarkable-cloud document tool on the exact active admission.
- The first completion recovery followed only whatever transcript =agent:main:main= currently referenced; a later session remap made one successfully completed selection look like a timeout. The bridge now captures the pre-turn transcript id for bounded exact-file fallback while deliberately omitting unsafe =chat.send.sessionId= repinning.
- The first captured-transcript fallback assumed OpenClaw retained =<session-id>.jsonl=. A real reset renames it to =<session-id>.jsonl.reset.<timestamp>=, while a live final or replacement-session history could otherwise bypass exact transcript identity. Recovery now handles only bounded exact reset names with session-header/anchor validation, and reMarkable prompt/tool authority is bound to the captured transcript. The bridge also forwards the fixed routing contract so a configuration drift cannot silently change what =agent:main:main= means.
- The first plugin receipt reader used path-based =readFile= and could follow a symlinked =record.json= into a forged cached success. Both WhatsApp and cloud-upload receipt journals now use no-follow descriptor reads with owner/type/identity, private-mode, single-link, 64 KiB, stable-read, and fatal UTF-8 checks before parsing.
- The first transient runner waited only for the Smart Remarkable process and could leave a stale ready marker after its SSH tunnel died. The runner now supervises both children, and AppLoad independently health-checks the fixed forwarded bridge before accepting either native-button trigger.
- The first trusted-origin implementation passed a plugin-realm object to OpenClaw's public =runContext.setRunContext= API before =chat.send=. OpenClaw 2026.7.1 validates plain-object prototype identity in the host realm, and the live write returned =false= before admission. A plugin-instance Map was considered next, but OpenClaw can keep separate startup, active-hook, and pinned-tool registries, so those Maps would not share authority. A realm-neutral scalar then passed split-registry unit tests, but live bind still returned =UNAVAILABLE=: the Gateway method was calling the ordinary plugin run-context facade after plugin registration had closed, so the late write could not be treated as a usable host mutation. The current version retains the v2 scalar authority and its exact run/transcript checks, but reaches host get/set/clear through a registered synchronous agent-event subscription. The emitter places only a random operation id on the plugin-owned stream; the operation, scalar, capability, and cleanup handle never enter the event or run id. Exact read-back, bounded in-flight commands, opaque-handle cleanup, and missing/asynchronous receipt failure preserve the original fail-closed authority model.
- Automatic survival across firmware updates is no longer required. The user
  accepts an exact, hassle-free reinstall after each update. This changes only
  update orchestration: exact runtime fingerprints, offline composition,
  independent rollback, root-read-only checks, and physical acceptance remain
  required.
